# Что можно улучшить

## 1. Список данных для защиты и методы защиты

| # | Данные | Метод защиты | Инструменты |
|---|---|---|---|
| 1 | ФИО, дата рождения | **Шифрование** (AES-256) + **Обезличивание** для аналитики | Vault (HashiCorp), PostgreSQL column encryption |
| 2 | Телефон, email | **Шифрование** + **Маскирование** при отображении (+7 *** *** 78-90) | Маскирование на уровне API-ответа |
| 3 | Медицинские диагнозы | **Шифрование** + строгий **RBAC** (только лечащий врач) | Шифрование at-rest + TLS at-transit |
| 4 | Результаты анализов | **Шифрование** + **ABAC** (пациент видит только свои) | Row-level security в PostgreSQL |
| 5 | Данные платёжных карт | **Токенизация** (не хранить PAN) | PCI DSS-compliant платёжный шлюз |
| 6 | Имена папок / файлов | **Обезличивание** (UUID вместо ФИО) | Переименование в UUID при миграции |
| 7 | История посещений | **Обезличивание** для BI/ML, шифрование для оперативных данных | Data lakehouse с разделением уровней |
| 8 | Данные сотрудников | **Шифрование** + **RBAC** (только HR) | Отдельная схема БД, изолированный доступ |
| 9 | Бумажные анкеты | **Физическая защита** + **Оцифровка с шифрованием** + уничтожение | Регламент, шредер, аудит |

## 2. Механизм тегирования данных

### 2.1 Концепция тегирования

Каждый атрибут данных должен получать теги по трём осям:

```
{data_class}:{sensitivity}:{retention}

Примеры:
  pii:high:5y          — персональные данные, высокая чувствительность, хранить 5 лет
  medical:critical:10y — медицинские данные, критическая категория, хранить 10 лет
  financial:high:7y    — финансовые данные, высокая чувствительность, хранить 7 лет
  operational:low:1y   — операционные данные, низкая чувствительность, хранить 1 год
```


### 2.2 Инструменты тегирования

| Инструмент | Назначение | Применение |
|---|---|---|
| **Apache Atlas** | Каталог данных + тегирование | Маркировка полей в таблицах БД и файлах |
| **OpenMetadata** | Open-source альтернатива Atlas | Единый каталог метаданных |
| **PostgreSQL Row Security** | Политики доступа на уровне строк | Реализация ABAC в БД |
| **HashiCorp Vault** | Управление секретами и ключами | Шифрование чувствительных полей |
| **Apache Ranger** | Политики доступа | Контроль доступа к данным в озере данных |
| **Elastic SIEM** | Мониторинг и алертинг | Обнаружение аномального доступа |

## 3. Инструменты и меры обеспечения конфиденциальности

### 3.1 Privacy By Design — 7 принципов и реализация

| Принцип | Текущее состояние (AS-IS) | Целевое состояние (TO-BE) |
|---|---|---|
| Проактивность | Реактивный подход | Privacy Impact Assessment до разработки |
| Privacy as Default | Данные открыты по умолчанию | Минимум данных, доступ по явному запросу |
| Встраивание в дизайн | Не учтено | Шифрование и RBAC с первого дня |
| Полная функциональность | Безопасность vs. удобство | И безопасность, И удобство |
| Сквозная защита | Только в домене | Шифрование at-rest + in-transit |
| Видимость и прозрачность | Нет аудита | Полный аудит лог, Data Lineage |
| Уважение к пользователю | Нет права на удаление | Механизм удаления/обезличивания |

### 3.2 Data Minimization — меры

- Собирать только те поля, которые необходимы для конкретного процесса
- Разделить «операционную» и «аналитическую» копии данных
- Для BI/ML использовать только обезличенные данные (псевдонимизация/агрегация)
- Автоматическое удаление данных по истечении срока хранения (retention policy)

### 3.3 Data Lineage — инструменты

- **Apache Atlas / OpenMetadata** — граф происхождения данных
- **dbt (data build tool)** — линейность преобразований в Data Lake
- Логирование всех операций чтения/записи в централизованный SIEM
- Структурированные логи со стандартными полями (идентификатор пользователя, тип данных, тип действия, таймштамп и т.д.)
