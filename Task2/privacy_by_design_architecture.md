**Медикаменте**

Privacy by Design — целевая архитектура (TO-BE)

# **1. Введение**
Данный документ описывает целевую (TO-BE) архитектуру системы «Медикаменте», спроектированную с применением принципов Privacy by Design. Диаграмма C4 TO-BE содержит минимальный набор компонентов, которые напрямую реализуют принципы защиты конфиденциальности — чтобы показать связь каждого компонента с конкретным принципом PbD и конкретной проблемой из Task1 (AS-IS).

Полный набор компонентов, необходимых для промышленного (продуктового) решения, описан в разделе 5. Такое разделение позволяет сначала понять «зачем» каждый блок, и только затем говорить о «как» его реализовать.

# **2. Что и почему вошло в диаграмму**
Каждый компонент диаграммы закрывает минимум одну критическую проблему AS-IS и реализует конкретный принцип Privacy by Design. Ниже — обоснование каждого решения.

## **2.1 Блок Privacy Gateway — новый блок**

|**Компонент**|**Принцип PbD**|**Закрытые проблемы**|**Обоснование включения**|
| :- | :- | :- | :- |
|API Gateway|End-to-End Security|P-04 (нет TLS)|Единственная точка входа — TLS 1.3 на всех входящих соединениях. Снаружи нет прямого доступа ни к одному сервису. Rate-limiting предотвращает брутфорс.|
|IAM / SSO|Privacy as Default, Least Privilege|P-02 (нет RBAC)|Устраняет главную проблему AS-IS: вход в домен ≠ доступ ко всему. RBAC-роли (DOCTOR, ADMIN, CASHIER, WAREHOUSE) выданы явно. JWT несёт role + scope.|

**Consent Service** (управление согласиями пациентов и право на забвение по ст. 21 152-ФЗ) не включён в диаграмму, но описан в разделе 5 как обязательный компонент продуктового решения.

## **2.2 Бизнес-сервисы — доработанные**
Структура бизнес-сервисов соответствует AS-IS, однако каждый сервис доработан с учётом принципов Data Minimization и Privacy Embedded into Design:

|**Изменение в сервисе**|**Принцип PbD**|**Закрытая проблема**|
| :- | :- | :- |
|patient\_uuid вместо ФИО во всех API, URL и хранимых ссылках|Data Minimization|P-03: ФИО исчезает из имён папок, URL, логов файловой системы|
|ABAC в Appointment / Medical Records: врач видит только своих пациентов|Privacy as Default|P-02: невозможность доступа к данным вне своей области ответственности|
|Lab Integration: mTLS API вместо email, row-level security для пациента|End-to-End Security|P-07: результаты анализов не передаются по незашифрованной почте|
|Payment Service: токенизация, PAN не хранится локально|Privacy Embedded into Design|P-04, P-08: платёжные данные не могут утечь из локальной системы|
|Уведомления: payload содержит только patient\_uuid + дата, без ФИО|Data Minimization|P-10: ФИО и медданные не попадают в тело SMS / Push-уведомлений|
|1С переведена в клиент-серверный режим (PostgreSQL), RBAC внутри 1С|Privacy Embedded into Design|P-08: файл базы данных больше нельзя скопировать напрямую|

## **2.3 Блок Data & Privacy Infrastructure — новый блок**

|**Компонент**|**Принцип PbD**|**Закрытые проблемы**|**Обоснование включения**|
| :- | :- | :- | :- |
|Operational DB (PostgreSQL + RLS)|Privacy Embedded into Design|P-01 (нет шифрования)|Row Security Policies защищают данные на уровне СУБД — независимо от кода приложения. PII-поля зашифрованы через pgcrypto. Даже при утечке дампа данные нечитаемы.|
|Key Vault (HashiCorp Vault)|Privacy Embedded into Design|P-01 (нет управления ключами)|Централизованное управление ключами шифрования. Ротация ключей по расписанию. Dynamic secrets: сервис получает временные учётные данные к БД. Audit log всех операций с ключами.|
|Audit Log (ELK Stack)|Visibility & Transparency|P-05 (нет аудита доступа)|Каждое обращение к ПДн фиксируется: user\_id, action, resource\_id, data\_class, timestamp. DPO видит полную историю доступа. Алертинг при аномальных паттернах (например, массовая выгрузка медкарт).|

## **2.4 Аналитический слой — новый блок**
Ключевой принцип слоя: аналитики никогда не работают с ПДн напрямую. Данные проходят через обезличивающий ETL до того, как попасть в любой аналитический инструмент.

|**Компонент**|**Принцип PbD**|**Что даёт**|
| :- | :- | :- |
|ETL / Anonymizer|Data Minimization|Автоматически обезличивает данные: ФИО → UUID, агрегация по периодам, k-anonymity для редких значений. Без прохождения через этот компонент данные не попадают в аналитику — это архитектурный запрет.|
|Anonymized DWH|Full Functionality|Изолированное хранилище без прямых идентификаторов пациентов. Единственный разрешённый источник для BI. Аналитика работает в полную силу — и при этом не нарушает конфиденциальность.|
|BI / Reports (Apache Superset)|Full Functionality|P&L, ABC-анализ, загрузка специалистов — прямой доступ к Operational DB закрыт на уровне сети и IAM. Это реализует принцип «и безопасность, и функциональность» — бизнес получает нужные отчёты без риска утечки ПДн.|


# **3. Соответствие 7 принципам Privacy by Design**

|**Принцип PbD**|**Реализация в TO-BE**|
| :- | :- |
|1\. Proactive, not Reactive|Шифрование, RBAC, аудит — встроены в архитектуру до первой строки кода. Privacy Impact Assessment проводится до начала разработки.|
|2\. Privacy as Default|Минимум данных по умолчанию: API отдаёт только то, что разрешено ролью. Пациент видит только свои данные без дополнительных настроек.|
|3\. Privacy Embedded into Design|TLS, RLS в СУБД, шифрование полей через Key Vault, токенизация платежей — реализованы на уровне инфраструктуры, не зависят от кода разработчика.|
|4\. Full Functionality|Врач работает эффективно (ABAC на своих пациентов), аналитик строит отчёты (Anonymized DWH) — безопасность не мешает функциональности.|
|5\. End-to-End Security|TLS 1.3 снаружи → TLS между сервисами → зашифрованные поля в БД (Key Vault) → зашифрованные резервные копии.|
|6\. Visibility & Transparency|Audit Log фиксирует каждое обращение к ПДн. DPO видит полный граф доступа. Key Vault ведёт свой audit log операций с ключами.|
|7\. Respect for User Privacy|Consent Service (раздел 5) реализует ст. 21 152-ФЗ: пациент управляет согласием и может инициировать удаление своих данных.|

# **5. Компоненты продуктового решения**
Следующие компоненты не включены в диаграмму Задания 2, но их следует включить в промышленную реализацию системы. Каждый компонент описан с указанием принципа PbD, который он реализует, и рекомендуемым инструментом.

## **5.1 Consent Service — управление согласиями**
Принцип PbD: Respect for User Privacy. Нормативное требование: ст. 21 152-ФЗ.

Реализует право пациента на отзыв согласия на обработку ПДн и право на удаление своих данных («право на забвение»). При поступлении запроса на удаление сервис запускает workflow: находит все записи пациента по patient\_uuid во всех хранилищах, удаляет или обезличивает их, фиксирует факт выполнения. Фиксирует версию документа согласия с датой подписания — на случай претензий регулятора.

*Рекомендуемый подход: отдельный микросервис с собственной БД, интеграция с IAM (проверка согласия при выдаче токена). Инструменты: Spring Boot + PostgreSQL.*

## **5.2 Data Catalog — каталог данных с тегированием**
Принцип PbD: Visibility & Transparency.

Каталогизирует каждое поле каждой таблицы по таксономии {data\_class}:{sensitivity}:{retention}. Например, поле phone\_number получает тег pii:high:5y — персональные данные, высокая чувствительность, хранить 5 лет. Автоматически обнаруживает PII-поля (PII Discovery). Строит граф Data Lineage: откуда пришли данные, через какие трансформации прошли, куда попали. Интегрируется с Audit Log и Governance Portal.

*Рекомендуемые инструменты: Apache Atlas или OpenMetadata (open-source). Интеграция с dbt для Data Lineage аналитического слоя.*

## **5.3 Data Governance Portal — портал DPO**
Принцип PbD: Visibility & Transparency, Respect for User Privacy.

Единый интерфейс для ответственного за защиту данных (DPO). Функции: панель статуса согласий пациентов, очередь и трекинг запросов на удаление данных, автоматические отчёты для Роскомнадзора, настройка retention policies с автоматическим удалением по истечении срока, просмотр Data Lineage — для ответа на вопрос «где хранятся данные конкретного пациента».

*Рекомендуемые инструменты: Apache Atlas UI или OpenMetadata как базовая платформа, доработанная под нужды DPO.*

## **5.4 Event Bus (Apache Kafka) — шина сообщений**
Принцип PbD: End-to-End Security.

В предагаемом решениии Задания 2 сервисы пишут в Audit Log напрямую по REST. Проблема: если Audit Log временно недоступен, аудит-событие теряется. В продуктовом решении сервисы публикуют события в Kafka, Audit Log подписывается на топик — доставка гарантирована даже при перезапуске. Все топики Kafka шифруются TLS. Schema Registry с тегами чувствительности позволяет применять политики доступа на уровне топика.

*Рекомендуемые инструменты: Apache Kafka + Confluent Schema Registry + Kafka Connect для выгрузки в ELK.*

## **5.5 Raw Zone в Data Lake — двухуровневое хранилище**
Принцип PbD: Privacy Embedded into Design.

В представленной версии решения есть только Anonymized DWH. Для продуктового решении нужна двухуровневая структура. Raw Zone — зашифрованные необработанные данные с доступом строго ограниченным до роли Data Engineering. Anonymized Zone — обезличенные данные для аналитиков и BI-инструментов. Raw Zone необходима для повторной обработки при изменении алгоритма обезличивания, для forensic-анализа инцидентов (с соблюдением RBAC) и для выполнения требований законодательства о хранении первичных данных.

*Рекомендуемые инструменты: MinIO (self-hosted S3-совместимое хранилище) с политиками доступа через IAM.*

## **5.6 ML / AI Platform**
Принцип PbD: Full Functionality.

На обезличенных данных Anonymized DWH можно обучать модели: оптимизация расписания специалистов, прогнозирование спроса на услуги, ABC-анализ медикаментов. Обязательное условие: только Anonymized DWH как источник данных. Дополнительная защита — дифференциальная приватность (Differential Privacy) при обучении моделей: в модель добавляется математически обоснованный шум, который гарантирует, что по параметрам модели нельзя восстановить данные конкретного пациента.

*Рекомендуемые инструменты: Jupyter + MLflow для экспериментов, библиотека Google DP или PyDP для дифференциальной приватности.*
